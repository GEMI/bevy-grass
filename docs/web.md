# Running in the browser

bevy_grass runs in browsers through WebGPU, with the same shaders, buffers
and settings as on native: there is no second renderer and no web-only code
path. This page covers what differs: what a browser needs, where it has been
tested, and how fast it is.

The [web demo](https://gemi.github.io/bevy-grass/) is a meadow with a quality
switch and every preset. Its source is [`web/`](../web/).

## Build a game for the browser

Turn on Bevy's `webgpu` feature for wasm. On wasm, Bevy's default features
render through WebGL2, which has no compute shaders, so grass would draw
nothing; `webgpu` replaces it:

```toml
[target.'cfg(target_arch = "wasm32")'.dependencies]
bevy = { version = "0.20", features = ["webgpu"] }
```

- **WebGL2 is not supported**, and will not be: blades are generated by
  compute shaders. On a WebGL2 build grass logs one warning, draws nothing,
  and `GrassSupport` is `NoComputeShaders`; the rest of the scene renders.
- **Bevy's `file_watcher` does not build for wasm** (it is a
  `compile_error!`), so turn it on for native targets only if you use it to
  reload `.grass.ron` files.
- **WebGPU needs a secure context:** HTTPS, or `http://localhost`. A page
  served over a LAN address gets no WebGPU.
- **The wasm is large.** The demo is 18.2 MiB (5.3 MiB gzipped) with the
  size settings in this repository: a profile with `opt-level = "s"` and fat
  LTO, `wasm-bindgen --remove-name-section`, `wasm-opt -Os`, and only the
  Bevy features it draws with. A plain release build of an example is
  64.8 MiB with its function names stripped. [`tools/web_demo.py`](../tools/web_demo.py) does every step and
  is a starting point for a game's own build.

[`examples/webgpu_minimal.rs`](../examples/webgpu_minimal.rs) is the README's
quick start with these choices made: a canvas that fills the page, `LOW` on
the web, and a message on screen when the device cannot draw grass.
`python tools/web_example.py webgpu_minimal` builds it and serves it on
localhost.

## Browsers

| Browser | Result |
| --- | --- |
| Edge 155, Windows (Intel UHD Graphics, Xe) | Draws: wind, shadows, trampling, far grass. No errors. |
| Brave 1.97 (Chromium 155), Windows (NVIDIA T1200) | Draws, at every quality tier. No errors. |
| Chrome 147, Windows | Fails: the browser rejects every indirect dispatch ("ImmediateAddressSpace feature is not enabled"). A browser bug, gone in Chromium 155. |
| Chrome and Safari on macOS, Firefox, Chrome on Android | Not tested yet. |

To test a browser, run `python tools/web_demo.py serve` and open
`http://localhost:8080/?smoke`: the page steps through every quality tier and
posts a report of the adapter, its limits, blade counts, frame times and any
error back to the terminal. [Testing](testing.md) has the details, and how to
reach a phone over USB.

## What a device needs

Grass checks the device once, when the renderer starts. A device that falls
short of any of these draws no grass and logs one warning saying which; the
`GrassSupport` resource says the same, for a game that wants to tell the
player or hide its grass settings:

| Needs | WebGPU | Short of it |
| --- | --- | --- |
| Compute shaders, indirect dispatches and draws, storage buffers in the vertex shader | Core: every WebGPU device has them | `NoComputeShaders`, `NoIndirectExecution`, `NoVertexStorage` (WebGL2) |
| 10 storage buffers per shader stage | Optional above the spec's 8; [98% of devices](https://web3dsurvey.com/webgpu/limits/maxStorageBuffersPerShaderStage) offer 10 or more, but most of Chrome on macOS offers fewer than 16 | `TooFewStorageBuffers`, with both numbers |
| A 128,000,000-byte storage binding, for a camera's blades at `GrassSettings::MAX_INSTANCE_CAPACITY` | Every device: the spec's minimum is 128 MiB (134,217,728 bytes) | `StorageBindingTooSmall` |

Grass binds its storage buffers in the vertex and compute stages only, so it
adds nothing to the fragment-stage storage buffers Bevy's own lighting uses.
[Bind groups and the storage-buffer budget](rendering.md#bind-groups-and-the-storage-buffer-budget)
has the layout of every pipeline.

**Masks and heightmaps share one storage binding**, so together they must fit
the device's largest one, which is at least 128 MiB. A 4096 × 4096 heightmap is 64 MiB, and a density mask of that size
32 MiB. If the fields' masks and heightmaps add up to more, grass logs one
warning and draws nothing until they shrink. Unlike the checks above, this
one depends on the fields, so `GrassSupport` does not show it.

## Shadows

Grass casts shadows only on a device with the optional `depth-clip-control`
feature. Bevy's directional shadow maps clamp geometry behind the light's
near plane instead of clipping it, and grass does the same; without the
feature grass casts no shadow rather than a wrong one, and still receives
shadows from everything else. Edge 155 and Brave 1.97 on Windows have it;
the demo's `?smoke` report lists a browser's features.

## Timing

Bevy measures GPU time per pass with timestamps written into the command
encoder, which WebGPU does not allow. In a browser the per-pass GPU times
(the examples' `--perf` and Bevy's render diagnostics) are therefore missing,
and only frame time is left: the demo measures it with
`requestAnimationFrame`, so anything faster than the display's refresh shows
as one refresh. `GrassStats` and the `grass/` diagnostics (blades,
overflows, rebuilds) work as on native.

## How fast it is

Grass costs much more in a browser than natively on the same GPU, and why is
not known yet. On the Intel GPU below, `meadow` took 30.5 ms a frame in Edge
against 8.4 ms with no grass, at 1896 × 988; natively the same GPU spends
under 1 ms on grass. Turning off the browser's bounds checks and validation
changed nothing. Bevy without grass is slower in the browser too, about
8.4 ms against 4 ms natively.

Until that is understood, start the web build lower than native and let the
player change it. Measured so far, in the demo, frame time at p95 with vsync
at 60 Hz (16.7 ms is a full 60 Hz):

| Device | Browser | Window | Low | Medium | High | Ultra |
| --- | --- | --- | --- | --- | --- | --- |
| Integrated laptop GPU (Intel UHD, Xe) | Edge 155 | Full window | 16.8 ms | 33.3 ms | 50.1 ms | 66.7 ms |
| Integrated laptop GPU (Intel UHD, Xe) | Edge 155 | 800 × 600 | 16.9 ms | 16.8 ms | 16.8 ms | 33.4 ms |
| Discrete laptop GPU (NVIDIA T1200) | Brave 1.97 | 800 × 600 | 16.9 ms | 16.8 ms | 16.9 ms | 16.9 ms |
| Macs, phones and desktop GPUs | | | not measured | | | |

So on an integrated GPU `LOW` is the tier that holds 60 Hz in a full window.
The demo starts at `MEDIUM`, a guess for devices not measured yet.

**wasm runs on one thread.** Rebuilding the field tables, after a field, a
mask or a heightmap changes, runs on the main thread there, and masks
and heightmaps download over HTTP before a field grows. How long a rebuild
of a large terrain takes in a browser is not measured yet; `GrassStats`
reports the last one (`grass/rebuild_time`), so check it on your own fields.
